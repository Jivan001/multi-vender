ABSTRACT

CampusCart is an educational front-end prototype of a multi-vendor e-commerce platform. It provides a single marketplace where a user can browse products from multiple vendors, search and filter the catalogue, add items to a cart, complete a simulated checkout, track a demo order and view a generated invoice. A simple vendor desk permits product addition to the browser-stored catalogue.

The project is implemented using HTML5, CSS3 and vanilla JavaScript. Browser localStorage is used only for demo persistence. The project has no server, database, real authentication, secure payment gateway, inventory service or shipping integration. Its purpose is to demonstrate the visible workflow and user-interface logic of a marketplace in a clear form suitable for an MCA SIP presentation.

Keywords: Multi-vendor marketplace, e-commerce, front-end prototype, HTML, CSS, JavaScript, localStorage.

Chapter 1: Introduction

1.1 Background

Online marketplaces bring products from more than one seller into a single shopping experience. A customer expects to discover items quickly, compare options, maintain a cart and receive a clear order summary. Vendors need a way to present products. CampusCart models this idea as a small academic prototype for student-oriented products.

1.2 Problem Statement

Building a full e-commerce marketplace is complex because it requires multiple roles, product data, cart calculations, payments, orders and delivery updates. For a front-end SIP demonstration, the core challenge is to present these connected user flows clearly without claiming backend facilities that are not implemented.

1.3 Proposed Solution

CampusCart provides a responsive web interface containing a product catalogue, filtering and search, cart, simulated checkout, order tracking, invoice view and a simulated vendor product-entry desk. Data changes remain available in the same browser through localStorage.

1.4 Objectives

  1. To create a clear multi-vendor product catalogue.
  2. To implement client-side product search, filter and sorting functions.
  3. To implement cart quantity management and total calculation.
  4. To demonstrate a simulated checkout, order tracking and invoice flow.
  5. To demonstrate a local vendor catalogue operation.
  6. To produce a responsive and accessible interface that is easy to explain in a viva.

1.5 Scope

The scope is limited to front-end interaction. It covers a product catalogue, local cart, demo checkout, order presentation, invoice display and a vendor form. It does not cover live user registration, login, server APIs, payment collection, database storage, tax calculation or delivery-provider integration.

Chapter 2: Requirement Analysis

2.1 Functional Requirements

ID Requirement
FR-01 User can view products from different vendors.
FR-02 User can search, filter by category/vendor and sort products by price.
FR-03 User can add, remove and update product quantities in the cart.
FR-04 User can submit a simulated checkout form.
FR-05 System can show a demo order status and invoice.
FR-06 Vendor can add a product to the current browser catalogue.
FR-07 Product, cart and order data can persist locally in the browser.

2.2 Non-Functional Requirements

Area Requirement
Usability Simple labels, visible demo notices and predictable navigation.
Responsive design Layout adapts to desktop and mobile screens.
Accessibility Semantic controls, readable contrast, labels and keyboard-operable buttons.
Performance Fast local loading with no third-party libraries or network dependency.
Security boundary No sensitive data should be entered; localStorage is not secure storage.

2.3 Feasibility

Technical: feasible with standard browser technologies. Economic: no license cost is required. Operational: a browser is sufficient. The limitation is that it is a demonstration, not an operational e-commerce service.

Chapter 3: System Design

3.1 Technology Stack

Technology Purpose
HTML5 Page structure, forms, dialogs and semantic content.
CSS3 Responsive layout, typography, colour system and print styling.
JavaScript (ES6) Rendering, filtering, cart logic, checkout, invoice and order status.
localStorage Browser-only demo persistence for product, cart and order arrays.

3.2 Module Design

Module Responsibility
Catalogue Displays products and applies user-selected filters and sorting.
Cart Stores selected product identifiers, quantities and calculates totals.
Checkout Collects demo customer details and creates a local order object.
Orders & Invoice Shows demo progress and a readable order invoice.
Vendor Desk Adds products to the browser-only catalogue and shows vendor totals.

3.3 Workflow

Browse Catalogue→Search / Filter→Add to Cart→Simulated Checkout→Order / Invoice

The vendor workflow is: Vendor Desk → Fill Product Form → Add to local catalogue → Product appears in the catalogue. There is no role validation because there is no backend authentication.

3.4 Data Design

Products are represented by id, name, price, category, vendor and emoji. Cart items contain id and quantity. Orders store id, date, customer, address, simulated payment method, items and total. These JavaScript objects are serialised to localStorage.

Chapter 4: Implementation

4.1 Application Structure

File Purpose
index.html Interface sections: header, catalogue, vendor desk, orders, write-up and dialogs.
styles.css Design tokens, responsive grid, dialogs, cart panel and print styles.
app.js Product rendering, events, localStorage operations, calculations and demo orders.

4.2 Main Logic

On startup, the application loads saved data from localStorage. If none is found, it uses an initial product list. A rendering function applies search, category, vendor and price sorting before displaying cards. Cart updates change the stored quantity and recalculate the total. Checkout converts cart content into a new order and clears the cart. The order status changes visually after a short interval solely to demonstrate tracking.

4.3 Validation

Required fields in product and checkout forms use browser validation. Price input accepts values above zero. The checkout action is unavailable when the cart is empty. However, client-side validation is not security; a real system must validate all inputs on the server.

4.4 User Interface Choices

The interface uses a restrained colour palette, high-contrast controls, grouped content and short labels. The demo boundary is visible near the top of the application and repeated at checkout and invoice screens. This prevents the user from mistaking the prototype for a live commercial platform.

6.5 Observed Result

The prototype provides a connected, understandable flow from catalogue browsing to a simulated purchase record. The data remains available after refresh on the same browser because localStorage is used. The project meets its declared front-end objectives. It is intentionally limited to a single-browser demo and should not be deployed as an actual marketplace.

Chapter 7: Limitations and Future Work

7.1 Limitations

  • No user account creation, login, password handling or role-based access control.
  • No server, REST API, database or shared multi-user data.
  • Payment options are visual simulations; no money is collected or processed.
  • Product stock and delivery status are not connected to real services.
  • localStorage can be edited or cleared by the user and is not safe for sensitive data.
  • Invoice is a demonstration view and not a legal, tax or payment document.

7.2 Future Enhancements

  • Develop a backend using a suitable server framework and database.
  • Add secure authentication with separate customer, vendor and administrator roles.
  • Store products, carts and orders in a database with server-side validation.
  • Integrate a compliant payment provider through secure server-side APIs.
  • Add inventory management, vendor approval, image upload and shipment integration.
  • Add formal unit, integration, security and accessibility testing.

Conclusion

CampusCart demonstrates the core visible interactions of a multi-vendor e-commerce platform using HTML, CSS and JavaScript. It successfully shows product discovery, filtering, cart management, simulated checkout, order tracking, invoice display and local vendor catalogue operations. The work is valuable as a front-end proof of concept. A full production solution would require the backend, security and integrations described in the future-work section.

Appendix A: Run Instructions

  1. Open the folder containing the project files.
  2. Open index.html in a modern web browser.
  3. Use the catalogue to add products to the cart.
  4. Open the cart and select “Continue to checkout”.
  5. Enter sample non-sensitive information and place a simulated order.
  6. Open the Orders section to view tracking and invoice.
  7. Use “Reset all demo data” before a fresh presentation, if required.

Appendix B: Viva Questions

  1. Why localStorage? It provides simple browser-side persistence for an offline front-end demonstration.
  2. Is payment real? No. It is deliberately marked as a simulated front-end feature.
  3. What is required for production? Backend APIs, database, authentication, validation, security, payment-provider integration and testing.
  4. What makes this multi-vendor? Products are associated with distinct vendor names and the interface includes vendor-oriented catalogue entry.

            function renderProducts() {
                let list = [...products]
                  , q = $('#search').value.trim().toLowerCase()
                  , cat = $('#category').value
                  , vendor = $('#vendorFilter').value
                  , sort = $('#sort').value;
                if (q)
                    list = list.filter(p => `${p.name} ${p.vendor} ${p.category}`.toLowerCase().includes(q));
                if (cat !== 'all')
                    list = list.filter(p => p.category === cat);
                if (vendor !== 'all')
                    list = list.filter(p => p.vendor === vendor);
                if (sort === 'low')
                    list.sort( (a, b) => a.price - b.price);
                if (sort === 'high')
                    list.sort( (a, b) => b.price - a.price);

Try clearing a filter.</div>'
            }
